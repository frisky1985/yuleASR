## 2 原因分析

### 2.1 根本原因分类

| 编号 | 原因类别 | 描述 | 影响程度 |
|------|----------|------|----------|
| RC-01 | 外部依赖不可模拟 | Csm 模块通过 CryIf 接口调用底层加密库 (Crypto Library), 测试环境中无可用加密库 mock 实现 | 高 |
| RC-02 | 嵌套 fallback 路径复杂 | 每个加密 API 均有 CryIf -> 硬件服务层 -> 软件 fallback 三层回退, 嵌套深度达 4-5 层 | 高 |
| RC-03 | 测试环境限制 | host-based 单元测试无法链接真实 HSM (Hardware Security Module) 驱动, 无法触发硬件路径 | 中 |
| RC-04 | 配置组合爆炸 | Csm 支持 AES/HMAC/RSA/ECDH 等多种算法组合, 完整覆盖需数百个测试用例 | 中 |

### 2.2 原因详细说明

#### RC-01: 外部依赖不可模拟

Csm 模块通过 `CryIf_KeyDerive()`, `CryIf_KeyExchangeCalcPubValue()`, `CryIf_MacVerify()` 等接口调用底层加密库。当前测试环境中:

- CryIf 层仅有接口定义, 无完整的 mock 实现
- 加密库 (如 NXP CSEc / HSM 驱动) 需要真实硬件或商业模拟器
- 内部加密算法 (AES/HMAC/ECDH) 的软件实现在测试构建中被裁剪

这导致 `Csm_KeyDerive()` 等函数在调用 `CryIf_*()` 后直接走 fallback 路径, 无法测试 CryIf 成功路径及其后续逻辑。

#### RC-02: 嵌套 fallback 路径复杂

以 `Csm_KeyDerive()` 为例, 其调用链为:

```
Csm_KeyDerive()
  -> Csm_FindKeyIndex()           // 密钥查找
  -> 密钥状态/权限校验            // 多层 if-else
  -> CryIf_KeyDerive()            // 第一层: 加密库接口
  -> [失败] -> 硬件服务层遍历     // 第二层: Job 配置遍历
     -> Csm_FindJobIndex()        // 第三层: Job 查找
     -> 密钥材料复制              // 第四层: 元素有效性检查
     -> 同步/异步分发             // 第五层: 执行模式分支
```

每一层都有独立的错误处理和 fallback 逻辑, 导致分支数量指数级增长。完全覆盖需要构造:
- 有效的密钥配置 + 无效的密钥配置
- CryIf 成功 + CryIf 失败
- Job 存在 + Job 不存在
- 同步模式 + 异步模式
- 密钥元素有效/无效/长度为0/超长

#### RC-03: 测试环境限制

- 项目使用 host-based GCC 编译 + lcov 覆盖率测量
- 无法在 host 环境链接 NXP S32K312 HSM 驱动
- 无商业加密模拟工具 (如 VectorCAST, Cantata) 授权

#### RC-04: 配置组合爆炸

Csm 模块支持的算法和服务类型:

| 服务类型 | 算法 | 配置参数 |
|----------|------|----------|
| 密钥派生 | HKDF-SHA256, TLS-PRF, SP800-108 | 密钥长度, 输入参数 |
| 密钥交换 | ECDH (NIST P-256), RSA (2048/4096) | 曲线类型, 密钥长度 |
| MAC 生成/验证 | AES-CMAC, HMAC-SHA256, AES-GMAC | 算法, 密钥长度 |
| 签名生成/验证 | RSA-PKCS1v15, ECDSA | 密钥长度, 哈希算法 |

完整覆盖所有算法 x 成功/失败 x 同步/异步 组合需 200+ 测试用例, 超出当前测试框架能力。

## 3 风险评估

### 3.1 Csm 模块在安全机制中的角色

依据安全架构文档 (safety-architecture.md), Csm 模块承担以下安全功能:

| 安全功能 | 关联安全目标 | ASIL | 说明 |
|----------|-------------|------|------|
| 密钥管理 | SG-001 (通信数据完整性) | ASIL B | 管理 SecOC 使用的对称密钥 |
| MAC 计算 | SG-001 | ASIL B | 为 SecOC 提供消息认证码 |
| 密钥派生 | SG-001 | ASIL B | 从主密钥派生会话密钥 |
| 密钥交换 | SG-001 | ASIL B | ECDH 密钥协商 (可选) |

### 3.2 未覆盖分支的危险度分析

对 264 个未覆盖分支按危险度分级:

| 危险度 | 定义 | 数量 | 占比 | 说明 |
|--------|------|:----:|:----:|------|
| **高** | 可能导致安全功能静默失效 | 18 | 6.8% | 密钥状态校验绕过、MAC 验证跳过 |
| **中** | 可能导致功能降级但可被检测 | 86 | 32.6% | fallback 路径未走、异步回调丢失 |
| **低** | 不影响安全功能正确性 | 160 | 60.6% | 配置边界检查、冗余错误处理 |

#### 高危分支详情

| 函数 | 高危分支 | 风险描述 |
|------|:--------:|----------|
| `Csm_MacVerify()` | 8 | 算法分支未覆盖可能导致错误算法被选中, MAC 验证结果不可信 |
| `Csm_KeyDerive()` | 6 | 密钥权限校验 fallback 未覆盖, 可能允许非授权密钥派生 |
| `Csm_SignatureVerify()` | 4 | 签名验证 fallback 未覆盖, 可能接受无效签名 |

### 3.3 风险评估结论

| 维度 | 评估 |
|------|------|
| **安全影响** | 中 — Csm 的安全功能 (MAC/密钥) 有上层 SecOC 和 E2E 作为冗余校验 |
| **发生概率** | 低 — 未覆盖路径多为极端 fallback, 正常运行不会触发 |
| **可检测性** | 高 — 密钥异常和 MAC 失败可通过 Dem 事件上报和 WdgM 监控检测 |
| **综合风险等级** | **可接受 (Acceptable)** — 在补偿措施到位的前提下 |

### 4.2 措施详细说明

#### CM-01: 代码审查

- **范围**: `src/bsw/services/csm/src/Csm.c` 全部 2860 行
- **方法**: 双人审查 (作者 + 审查者), 逐函数检查
- **重点**:
  - 所有密钥状态转换路径
  - MAC 验证算法选择逻辑
  - 密钥派生权限检查完整性
  - 异步回调错误处理
- **输出**: 审查报告, 记录发现的问题及处理结果

#### CM-02: 静态分析

- **工具**: cppcheck + MISRA C:2012 规则集
- **标准**: 零 Required 规则违规, Advisory 规则偏差已记录于 docs/compliance/misra-deviation-report.md

#### CM-03: 集成测试

- **范围**: Csm -> CryIf -> SecOC 完整调用链
- **测试场景**:
  - SecOC 消息认证: 正常 MAC 生成/验证
  - 密钥切换: 运行时更换 SecOC 密钥
  - 密钥失效: 密钥过期后的降级处理
- **环境**: HIL 台架 (NXP S32K312 EVB + 真实 HSM)

#### CM-04: HIL 测试

- **范围**: 所有 CryIf 硬件路径
- **测试场景**:
  - AES-CMAC 密钥生成/验证 (HSM 加速)
  - ECDH P-256 密钥交换 (HSM 加速)
  - 密钥存储/加载 (HSM 安全存储)
- **预期**: 覆盖当前 host 测试无法触发的硬件路径分支

#### CM-05: 故障注入

- **方法**: 通过 CryIf mock 注入以下故障:
  - `CryIf_KeyDerive()` 返回 `CRYIF_E_GENERAL_ERROR`
  - `CryIf_MacVerify()` 返回 `CRYIF_E_KEY_EMPTY`
  - `CryIf_KeyExchangeCalcPubValue()` 返回 `CRYIF_E_KEY_NOT_VALID`
- **验证**: 确认 Csm 正确走 fallback 路径并上报 Dem 事件

#### CM-06: 形式化审查 (FMEA)

- **范围**: Csm 密钥管理状态机
- **方法**: 逐状态转换分析故障模式
- **输出**: Csm_FMEA 分析表, 识别残留风险

## 6 结论

### 6.1 偏差总结

Csm (Crypto Service Manager) 模块当前分支覆盖率为 61% (420/684), 未达到 ISO 26262-6 §9.2 对 ASIL B 模块 80% 的要求。差距主要来源于:

1. 加密库 (CryIf) 在测试环境中不可模拟, 导致大量 fallback 路径无法覆盖
2. 加密算法配置组合爆炸, 完整覆盖需 200+ 测试用例
3. host-based 测试环境无法链接真实 HSM 硬件

### 6.2 风险判定

经分析, 264 个未覆盖分支中:
- **高危 18 个 (6.8%)**: 涉及密钥状态校验绕过和 MAC 验证算法选择, 但有上层 SecOC 和 E2E 作为冗余保护
- **中危 86 个 (32.6%)**: fallback 路径和异步回调, 功能降级但可被 Dem 事件检测
- **低危 160 个 (60.6%)**: 配置边界检查, 不影响安全功能正确性

综合评估, 未覆盖分支的残留风险等级为 **可接受 (Acceptable)**。

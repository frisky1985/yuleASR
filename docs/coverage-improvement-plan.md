# BSW 覆盖率提升计划

> **目标**: 分支覆盖率 50.6% → ≥60% (CI 门禁 `threshold_branch: 50.0` 已达, 提升质量至 60%)
> **基线日期**: 2026-10-11
> **ISO 26262 参考**: Part 6 §9.2 (软件单元测试覆盖率)

## 1. 现状分析

### 1.1 覆盖率测量基础设施

| 脚本 | 覆盖范围 | 状态 |
|------|----------|------|

### 1.2 核心问题

1. **HW 依赖代码稀释覆盖率**: Crypto HSM、FlexRay、IRQ 处理器、配置表等 HW-only 代码包含大量不可测试分支, 将原始覆盖率从 ~40% 拉低至 ~35%
2. **零覆盖模块多**: Xcp(381), CanNm(242), LinNm(226), Fee(224), Flash(172), CryIf(168), DcmTransfer(166), J1939Tp(163), J1939Nm(162) 等模块分支覆盖率为 0%
3. **已有测试未充分覆盖**: Com, ComM, NvM, Dem, PduR 等模块有测试文件但分支覆盖不足 40-60%
4. **ASIL 覆盖率脚本损坏**: `run_branch_coverage.sh` 编译失败, 无法产出可信数据

## 4. 门禁调整建议

当前 CI 配置 (`ci-config.yaml`) 使用绝对阈值:

```yaml
threshold_branch: 50.0    # 硬门禁
c_fail_under: 60          # 行覆盖率硬门禁
```

**建议**: Phase 1 完成后, 将排除规则纳入 CI, 使门禁基于"可测试代码"而非全量代码。具体:
- 在 `coverage-ci-wrapper.sh` 中增加 lcov `--remove` 过滤 HW 文件
- 保持 `threshold_branch: 50.0` 不变 (排除后 50% 是合理目标)
- 添加模块级门禁: ASIL B 模块 ≥60% (与 `module_thresholds_branch` 一致)

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| HW 排除规则过于宽泛 | 漏测软件逻辑 | 按文件精确排除, 不用通配符 |
| 新测试编译失败 | 阻塞 Phase 4 | 每个模块独立验证编译后再合入 |
| 覆盖率数据不一致 | CI 误判 | 统一使用 lcov + gcovr 双验证 |
| E2E Profile 测试依赖 CRC 实现 | CRC 变更导致回归 | E2E 测试使用已知向量, 不依赖内部实现 |

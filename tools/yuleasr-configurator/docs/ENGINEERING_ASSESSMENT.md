# yuleASR Configurator — 工程化可用性评估与优化建议

> 第一性原理视角：AUTOSAR BSW 工程师的核心任务是什么？
> **在 90+ 模块的参数空间中，找到一组满足硬件约束、跨模块一致性、AUTOSAR 规范的配置，生成可编译的 C 代码。**

## 二、第一性原理分析：工程师实际工作流

### 2.1 真实工作流程（非工具视角，而是用户视角）

```
1. 拿到硬件需求 → 选 MCU → 确定可用外设
2. 定义通信矩阵 → CAN/LIN/Ethernet 拓扑 → DBC/LDF 导入
3. 逐模块配置 → 但模块之间有 200+ 隐式依赖
   - CanIf 的 CanIfRxPduCfg 必须引用 Can 的 HardwareObject
   - PduR 的 routing path 必须匹配 Com 的 signal group
   - NvM block ID 不能冲突，且要与 Fee/MemIf 一致
4. 多 ECU 场景 → 同一网络上的 ECU 配置必须对齐
5. 配置变体 → 同一 ECU 的不同软件版本（量产/工程/诊断）
6. 验证 → 不仅是单模块 schema 校验，更要跨模块一致性
7. 生成代码 → 集成到构建系统 → 编译 → 上板测试
8. 迭代 → 修改 → 对比 → 回归验证
```

### 2.2 当前工具与真实工作流的差距

| 工作流步骤 | 工具支持度 | 差距 |
|:----------|:---------|:-----|
| MCU 选型 | 有芯片数据库 | 缺少外设能力可视化（哪些 CAN/LIN/SPI 可用） |
| 通信矩阵导入 | DBC 导入 | 缺 LDF(LIN)、ARXML 网络拓扑 |
| 逐模块配置 | 有 | **缺跨模块引用校验**（最大痛点） |
| 多 ECU 对齐 | 有骨架 | **无实质功能** |
| 配置变体 | 无 | **完全缺失** |
| 验证 | 单模块 schema | **缺跨模块一致性检查** |
| 生成→编译 | 生成 C 头文件 | 缺编译集成验证闭环 |
| 迭代对比 | 有 diff 视图 | 缺版本化配置管理 |

## 三、核心问题诊断

### 问题 1：跨模块引用校验缺失（P0）

**现状**：每个模块独立校验 JSON Schema，但模块间的引用关系完全靠用户记忆。

**后果**：
- CanIf 配了一个不存在的 Can HardwareObject → 编译通过但运行时崩溃
- PduR routing table 引用了未启用的模块 → 链接错误
- NvM block ID 重复 → 运行时数据覆盖

**第一性原理**：AUTOSAR 配置的本质是一个**有向图**，节点是模块实例，边是引用关系。校验必须在这个图上做，而不是在孤立节点上做。

### 问题 2：工程持久化缺失（P0）

**现状**：配置以扁平 JSON/YAML 存储，没有工程文件概念。

**后果**：
- 无法保存"我正在做什么"的状态（打开了哪些 tab、侧边栏折叠状态等）
- 无法区分"工程文件"和"导出的配置文件"
- 团队协作时无法 merge 工程状态

### 问题 3：多 ECU 是空壳（P1）

**现状**：project store 有 ECU 数据模型，但 UI 上只有一个 ECU 列表，没有实质管理功能。

**后果**：
- 实际项目中通常 2-8 个 ECU，当前工具只能配一个
- 无法做网络级配置（同一 CAN 总线上的 ECU 节点 ID 分配）

### 问题 4：配置变体完全缺失（P1）

**现状**：无。

**后果**：
- 量产项目通常需要 3-5 个配置变体（基础配置 + 功能开关组合）
- 用户必须在外部用文件复制来管理变体

### 问题 5：验证停留在单模块（P1）

**现状**：validateAll() 只检查单模块参数范围。

**后果**：
- 跨模块约束（如 "CanIf 引用的 Can Controller 必须 enabled"）不检查
- AUTOSAR 规范中的 inter-module constraints 不覆盖

## 四、优化路线图

### Phase A：补齐工程基础（2-3 周）

| 序号 | 优化项 | 原理 | 工作量 |
|:-----|:-------|:-----|:-------|
| A1 | 工程文件 (.yuleasr) | 分离"工程状态"和"配置数据"，支持 git 友好 | 3d |
| A2 | 跨模块引用校验引擎 | 构建模块引用图，检查 dangling reference | 5d |
| A3 | 多 ECU 实质功能 | ECU 编辑器 + 网络拓扑视图 | 5d |
| A4 | 配置变体管理 | 基础配置 + overlay 机制 | 4d |

### Phase B：提升工程效率（2-3 周）

| 序号 | 优化项 | 原理 | 工作量 |
|:-----|:-------|:-----|:-------|
| B1 | 批量参数操作 | 多选模块 → 批量设值/启用/禁用 | 2d |
| B2 | 配置模板/预设 | 常用配置模式一键应用（如 "CAN 网关模式"） | 3d |
| B3 | 编译集成验证 | 生成代码后自动触发编译，反馈错误到 UI | 3d |
| B4 | 配置版本快照 | 关键节点打 tag，支持回滚和对比 | 2d |

### Phase C：智能化（持续）

| 序号 | 优化项 | 原理 | 工作量 |
|:-----|:-------|:-----|:-------|
| C1 | AI 助手增强 | 从"问答"升级为"主动建议"（检测配置异常时主动提示） | 持续 |
| C2 | 自动补全引用 | 输入 CanIf 的 Can 控制器引用时，下拉显示可用的 Can Controller | 2d |
| C3 | 配置健康评分 | 综合覆盖率、一致性、规范符合度给出评分 | 3d |

## 五、优先级建议

```
立即做（本周）:
  └─ A2: 跨模块引用校验引擎 — 这是配置正确性的基石

近期做（本月）:
  ├─ A1: 工程文件持久化
  ├─ A3: 多 ECU 实质功能
  └─ C2: 自动补全引用

中期做（下季度）:
  ├─ A4: 配置变体管理
  ├─ B1: 批量操作
  └─ B3: 编译集成验证
```

## 六、总结

yuleASR Configurator 在**单模块参数编辑**和**代码生成流水线**上已经达到可用水平，92 个模块的 schema 覆盖和 Jinja2 模板体系是扎实的基础。

但从工程用户视角，**最大的缺口不在"编辑能力"，而在"工程管理能力"**：

1. **跨模块引用校验** — 配置正确性的最后一道防线
2. **工程持久化** — 从"工具"到"工程环境"的质变
3. **多 ECU / 配置变体** — 量产项目的刚需

建议优先投入 A2（跨模块引用校验），因为它是其他所有高级功能的基础——没有引用图，变体管理、批量操作、AI 建议都无法可靠工作。
